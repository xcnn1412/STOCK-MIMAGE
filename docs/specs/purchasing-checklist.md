# จัดซื้อ — เช็กลิสต์จัดซื้อของงาน (`/jobs/purchasing`)

แท็บใหม่ของ Jobs · ตัดสินใจกับเจ้าของ 2026-09-29 · ศัพท์: `CONTEXT.md` หัวข้อ "จัดซื้อ" · schema: `supabase/migrations/20260929_purchasing_checklist.sql` (ทดสอบกับ postgres 17 แล้ว 21 ข้อ)

## Problem Statement

งานที่ลูกค้าตอบรับแล้วมีของต้องซื้อ ต้องสั่ง หรือต้องจัดการหลายอย่างก่อนถึงวันงาน ตอนนี้จดกันใน LINE และกระดาษ ไม่มีที่เดียวที่บอกได้ว่างานไหนของครบหรือยัง ใครรับผิดชอบรายการไหน ของที่สั่งไปถึงไหนแล้ว และใช้เงินไปเท่าไรเทียบกับงบ

## Solution

แท็บ **จัดซื้อ** ในหน้า Jobs: เลือกงานจาก CRM มาผูก (งานละหนึ่งเช็กลิสต์) หรือสร้างเช็กลิสต์ทั่วไปที่ไม่ผูกงาน แล้วเพิ่มรายการเป็นข้อๆ แต่ละข้อมีประเภท (ซื้อ / สั่ง / อื่นๆ) และสถานะ 4 ขั้น **วางแผน → กำลังจัดซื้อ → รอจัดส่ง → เสร็จสิ้น** กดครั้งเดียวเลื่อนขั้น เห็นความคืบหน้าและเงินต่องาน รายการที่เลยกำหนดหรือใกล้วันงานถูกยกขึ้นมาเตือนทั้งในหน้านี้และหน้าแรก

## User Stories

1. As a ฝ่ายประสานงาน, I want ค้นชื่อลูกค้าหรือสถานที่แล้วสร้างเช็กลิสต์ของงานนั้น, so that ไม่ต้องพิมพ์ชื่องานและวันงานซ้ำ
2. As a ฝ่ายประสานงาน, I want สร้างเช็กลิสต์ทั่วไปที่ไม่ผูกงาน, so that ของใช้ส่วนกลางมีที่จด
3. As a ผู้ใช้, I want พิมพ์ชื่อรายการแล้วกด Enter หรือวางหลายบรรทัดทีเดียว, so that จดรายการได้เร็วเท่าจดใน LINE
4. As a คนไปซื้อของ, I want กดครั้งเดียวเลื่อนสถานะและเห็นผลทันที, so that ใช้ตอนอยู่หน้าร้านบนมือถือได้
5. As a คนไปซื้อของ, I want กรองเหลือเฉพาะรายการของฉัน, so that รู้ว่าวันนี้ต้องซื้ออะไร
6. As a ฝ่ายประสานงาน, I want เห็นความคืบหน้าและงบเทียบยอดจ่ายจริงของแต่ละงาน, so that รู้ว่างานไหนของยังไม่ครบและเงินเกินงบหรือไม่
7. As a ฝ่ายประสานงาน, I want รายการที่เลยกำหนดหรือใกล้วันงานขึ้นบนสุดพร้อมป้ายเตือน, so that ไม่มีของตกหล่นก่อนวันงาน
8. As a ผู้ใช้, I want สลับดูแบบบอร์ด 4 คอลัมน์ตามสถานะ, so that เห็นของทุกงานที่ค้างอยู่แต่ละขั้น
9. As a ผู้ใช้, I want คัดลอกรายการเป็นข้อความ, so that ส่งต่อใน LINE ได้
10. As a ผู้รับผิดชอบรายการ, I want ได้แจ้งเตือนเมื่อถูกมอบหมาย, so that ไม่ต้องรอคนบอก
11. As a ฝ่ายประสานงาน, I want บันทึกชุดรายการที่ใช้บ่อยแล้วกดใช้ซ้ำ, so that งานแบบเดิมไม่ต้องพิมพ์ใหม่
12. As a คนไปซื้อของ, I want แนบรูปสินค้าหรือใบเสร็จในรายการ, so that คนอื่นเห็นว่าซื้ออะไรมา
13. As a แอดมิน, I want การ์ดเตือนหน้าแรกเมื่อใกล้วันงานแต่ของยังไม่ครบ, so that รู้โดยไม่ต้องเปิดหน้าจัดซื้อ

## Implementation Decisions

### ขอบเขตและสิทธิ์

- เส้นทาง `/jobs/purchasing` อยู่ใต้ Jobs — proxy ไม่บังคับโมดูล jobs อยู่แล้ว (ดู CLAUDE.md) หน้านี้ทำเหมือนแท็บอื่นของ Jobs ไม่เพิ่มการตรวจโมดูล
- ทุกคนที่ล็อกอิน (`requireAuth`) สร้าง เพิ่ม แก้ และเปลี่ยนสถานะได้
- **ลบ** (เช็กลิสต์ / รายการ / ชุดสำเร็จรูป) ได้เฉพาะ: คนสร้างสิ่งนั้น, ผู้รับผิดชอบเช็กลิสต์, แอดมิน, ฝ่ายประสานงาน — ฟังก์ชันเดียว `canDelete` ใช้ทั้ง UI (ซ่อนปุ่ม) และ server (บังคับจริง)

### ข้อมูล

- ตารางตาม migration: `purchase_lists`, `purchase_items`, `purchase_templates` — RLS เปิด ไม่มี policy อ่านเขียนผ่าน service role ใน server เท่านั้น
- งานหนึ่งงานมีเช็กลิสต์ใบเดียว (unique index บน `crm_lead_id`) — สร้างซ้ำ = เปิดใบเดิม ไม่ใช่ error
- `purchase_lists.title`: ใบที่ผูกงานเก็บชื่อลูกค้า ณ ตอนสร้าง (การ์ด CRM ถูกลบแล้วเช็กลิสต์ยังอ่านได้) หน้าจอแสดงชื่อจาก CRM ถ้ายังผูกอยู่
- `purchase_lists.updated_at` ถูกแตะทุกครั้งที่รายการในใบเปลี่ยน
- ราคา = ยอดของทั้งรายการ ไม่ใช่ต่อหน่วย · จำนวนเป็นข้อความอิสระ ("2 กล่อง")
- รูปแนบ: บัคเก็ต `purchase-attachments` path `{listId}/{itemId}/{ts}_{rand}.{ext}` สูงสุด 4 รูปต่อรายการ ไฟล์ละไม่เกิน 5MB เฉพาะ jpeg/png/webp บีบฝั่ง client ด้วย `compressImage` ก่อนส่ง ลบรายการหรือเช็กลิสต์ต้องลบไฟล์ด้วย (`removeStorageByUrls`)
- ตารางยังไม่ถูกสร้าง (ยังไม่รัน migration): หน้าแสดงข้อความอธิบาย ไม่ล้ม · แผงเตือนหน้าแรกคืนค่าว่าง ไม่ทำให้หน้าแรกล้ม

### หน้าหลักโหลดอะไร

เช็กลิสต์ที่ยังมีรายการไม่เสร็จ + เช็กลิสต์ที่ขยับใน 30 วันล่าสุด (รวมใบว่างและใบที่เสร็จแล้ว) · `?past=1` = โหลดทั้งหมด · อ่านรายการแบบแบ่งหน้าทีละ 1,000 จนหมด (เพดาน PostgREST)

### กติกาล้วน (pure) — `purchasing-logic.ts`

| เรื่อง | กติกา |
|---|---|
| สถานะ | `planning` วางแผน → `purchasing` กำลังจัดซื้อ → `awaiting_delivery` รอจัดส่ง → `done` เสร็จสิ้น · เลื่อนขั้น = ขั้นถัดไปตามลำดับ · เลือกขั้นไหนก็ได้ผ่านเมนู (ถอยได้) |
| ประเภท | `buy` ซื้อ · `order` สั่ง · `other` อื่นๆ |
| วันอ้างอิงของเช็กลิสต์ | วันงานจาก CRM (`event_date`) ถ้าผูกงานและมีวัน ไม่งั้น `due_date` ของเช็กลิสต์ ไม่งั้นไม่มี |
| กำหนดของรายการ | `due_date` ของรายการ ถ้าว่างใช้วันอ้างอิงของเช็กลิสต์ |
| ความด่วน | รายการที่เสร็จแล้วไม่มีความด่วน · กำหนด < วันนี้ = **เลยกำหนด** · อีก 0–3 วัน = **ด่วน** · อีก 4–7 วัน = **ใกล้ถึง** · ไกลกว่านั้นหรือไม่มีกำหนด = ไม่มี (เกณฑ์เดียวกับแผง "หน้าที่ยังไม่ครบ") |
| เช็กลิสต์เสร็จ | มีอย่างน้อย 1 รายการ และทุกรายการเสร็จสิ้น (ใบว่าง = ยังไม่เสร็จ) |
| เรียงเช็กลิสต์ | ยังไม่เสร็จก่อน → วันอ้างอิงใกล้สุดก่อน (ไม่มีวันไว้ท้าย) → สร้างล่าสุดก่อน |
| เรียงรายการในใบ | `sort_order` แล้ว `created_at` — ไม่ย้ายรายการที่เสร็จลงล่าง |
| ตัวกรอง | ทำที่ระดับรายการ: สถานะ, ของฉัน (ผู้รับผิดชอบรายการ = ฉัน), คำค้น (ชื่อเช็กลิสต์ สถานที่ ชื่อรายการ ร้าน) · ใบที่ไม่เหลือรายการตรงเงื่อนไขถูกซ่อน · ไม่มีตัวกรอง = เห็นใบว่างด้วย |
| เงิน | งบรวม = ผลรวม `est_price` · จ่ายจริงรวม = ผลรวม `actual_price` · นับ "เสร็จแล้วแต่ยังไม่ใส่ยอดจ่ายจริง" |
| แผงเตือนหน้าแรก | เช็กลิสต์ที่มีรายการไม่เสร็จซึ่งมีความด่วน · เห็นได้เมื่อเป็นแอดมิน, ฝ่ายประสานงาน, คนสร้างหรือผู้รับผิดชอบเช็กลิสต์, หรือผู้รับผิดชอบรายการที่ค้างในใบนั้น |

ขีดจำกัดข้อมูล (ตรวจใน `validateItemInput` ฝั่ง server ทุกครั้ง): ชื่อรายการ 1–200 ตัวอักษร · จำนวน ≤ 60 · ร้าน ≤ 120 · ลิงก์ต้องขึ้นต้น `http://` หรือ `https://` และ ≤ 500 · เลขพัสดุ ≤ 80 · หมายเหตุ ≤ 1000 · ราคา 0–99,999,999 · วันที่รูป `YYYY-MM-DD` ที่มีอยู่จริง · เพิ่มครั้งละไม่เกิน 50 รายการ · ชื่อเช็กลิสต์ 1–120 · ชื่อชุดสำเร็จรูป 1–80 · ชุดสำเร็จรูปมีได้ 1–50 รายการ

### แจ้งเตือน

ชนิดใหม่ `job_purchase_assigned` และ `job_purchase_done` — ขึ้นต้น `job_` จึงอยู่หมวด "งาน" เอง · `reference_type = 'job'`, `reference_id` = id เช็กลิสต์ · ตัวสร้างลิงก์ทั้ง 3 ที่ (กระดิ่ง, toast, หน้า /notifications) ส่งชนิดที่ขึ้นต้น `job_purchase_` ไป `/jobs/purchasing?list=<id>`
ponytail: ใช้ reference_type เดิมแทนการเพิ่มค่าใหม่ใน CHECK ของตาราง notifications — ไม่ต้องแก้ constraint และไม่มีความเสี่ยงลำดับ deploy (แบบเดียวกับ `job_pool_*`)

### หน้าจอ

- แท็บ "จัดซื้อ" (EN "Purchasing", ไอคอน ShoppingCart) ต่อจาก "ติดตามงาน" ใน `jobs-nav.tsx`
- `page.tsx` (server) → `data.ts::getPurchasingSnapshot` → `purchasing-view.tsx` (client) — โครงเดียวกับ `/jobs/tracking`
- การเปลี่ยนแปลงทุกอย่างใช้ `useOptimistic` + `useTransition`: หน้าจอเปลี่ยนทันที ข้อมูลจริงตามมาจาก `revalidatePath` · ล้มเหลว = กลับค่าเดิมเอง + `toast.error` · ไม่เรียก `router.refresh()` ในเส้นทางสำเร็จ
- มุมมอง "ตามงาน": การ์ดต่อเช็กลิสต์ — ชื่อ วันงาน+นับถอยหลัง ความคืบหน้า แถบสีตามสถานะ งบ/จ่ายจริง ป้ายความด่วน · กางเองเมื่อมาจากลิงก์ `?list=` หรือมีรายการเลยกำหนด/ด่วน ที่เหลือหุบ
- มุมมอง "ตามสถานะ" (`?view=board`): 4 คอลัมน์ การ์ดรายการ ปุ่มเลื่อนขั้นบนการ์ด · จอใหญ่ลากข้ามคอลัมน์ได้ (HTML5 drag แบบ `job-kanban-board.tsx`) · มือถือเลื่อนแนวนอน
- ช่องเพิ่มเร็วท้ายการ์ด: Enter = เพิ่ม 1 รายการ · วางข้อความหลายบรรทัด = เพิ่มทีละบรรทัด
- หน้าต่างแก้รายการ: ทุกช่อง + รูปแนบ
- หน้าต่างสร้างเช็กลิสต์: เลือก "ผูกงานจาก CRM" (ค้นฝั่ง server หน่วง 300ms) หรือ "ทั่วไป" + เลือกชุดสำเร็จรูป (ไม่บังคับ)
- หน้าต่างชุดสำเร็จรูป: รายการชุด สร้าง แก้ ลบ
- สถานะบอกด้วยข้อความเสมอ ไม่ใช้สีอย่างเดียว · ปุ่มไอคอนมี `aria-label` · ใช้ได้ที่ความกว้าง 360px โดยไม่เลื่อนแนวนอนทั้งหน้า (ยกเว้นบอร์ดที่เลื่อนในกรอบของตัวเอง)
- ข้อความบนจอเป็นภาษาไทยแบบเดียวกับ `/jobs/tracking` (ป้ายแท็บมีสองภาษาตาม `jobs-nav.tsx`)

### หน้าแรก

การ์ดเต็มความกว้าง "ของยังไม่ครบ — ใกล้วันงาน" ใต้การ์ดเงินเดือน แสดงเมื่อมีแถวเท่านั้น แต่ละแถวลิงก์ไป `/jobs/purchasing?list=<id>`

### ผูกใบเบิก (เพิ่ม 2026-09-29 — เจ้าของสั่ง)

เป้าหมาย: ให้รู้ว่ารายการไหนเบิกเงินไปแล้วด้วยใบเบิกใบไหน โดยต้นทุนของงานยังมาจากใบเบิกทางเดียว (Finance → Costs) เช็กลิสต์ไม่ส่งยอดเข้าต้นทุนเอง จึงไม่นับซ้ำ

| เรื่อง | กติกา |
|---|---|
| ความสัมพันธ์ | รายการหนึ่งข้อผูกได้ใบเบิกเดียว (`purchase_items.expense_claim_id`) · ใบเบิกหนึ่งใบผูกได้หลายรายการ ข้ามเช็กลิสต์ได้ · ผูกซ้ำกับใบใหม่ = แทนที่ใบเดิม |
| ใบเบิกที่ผูกได้ | ประเภท event / other / advance ที่สถานะไม่ใช่ rejected และ cancelled — ไม่รวมเอกสารวงเงินสดย่อย (`claim_type = 'petty_cash'`) |
| ใครผูกใบไหนได้ | แอดมินผูกได้ทุกใบ · คนอื่นผูกได้เฉพาะใบเบิกที่ตัวเองเป็นผู้เบิก (กติกาเดียวกับ Finance: ไม่ใช่แอดมินเห็นเฉพาะใบของตัวเอง) |
| ใครเลิกผูกได้ | ทุกคนที่ล็อกอิน (เป็นการแก้รายการแบบหนึ่ง) — มี log ทุกครั้ง |
| ข้อมูลใบเบิกที่คนอื่นเห็น | เลขที่ใบเบิก + สถานะ เห็นได้ทุกคนที่เห็นเช็กลิสต์ · ชื่อใบเบิก ยอด และยอดรวมของรายการที่ผูก เห็นเฉพาะแอดมินและผู้เบิกของใบนั้น (ตัดออกตั้งแต่ฝั่ง server ไม่ส่งไป browser) |
| ยอดของใบเบิก | `claimEffectiveAmount` (ใบทดลองจ่ายที่เคลียร์แล้วใช้ยอดที่ใช้จริง) |
| ยอดไม่ตรง | ผลรวม "จ่ายจริง" ของทุกรายการที่ผูกกับใบนั้น (ทุกเช็กลิสต์) ต่างจากยอดใบเบิกเกิน 0.01 บาท = ขึ้นข้อความเตือน ไม่บล็อก |
| ใบเบิกถูกลบ | เลิกผูกเอง (ON DELETE SET NULL) |
| ใบเบิกถูกปฏิเสธ/ยกเลิกภายหลัง | ยังผูกอยู่ แต่แสดงสถานะให้เห็น |

Server actions เพิ่ม (กติกาเดียวกับตัวอื่น: `requireAuth` ก่อน, ตรวจทุกอาร์กิวเมนต์, คืน `{ error }`):

| Action | งาน | ActionType |
|---|---|---|
| `searchPurchaseClaims(query)` | ใบเบิกที่ผู้ใช้ผูกได้ สูงสุด 20 ใบ ค้นจากเลขที่หรือชื่อ เรียงใหม่สุดก่อน คืนจำนวนรายการที่ผูกอยู่แล้วของแต่ละใบ | — (อ่าน) |
| `linkPurchaseItemsToClaim(itemIds[], claimId)` | 1–50 รายการ · ทุก id ต้องมีอยู่จริง ไม่งั้นไม่ผูกเลยสักรายการ | `LINK_PURCHASE_ITEM_CLAIM` |
| `unlinkPurchaseItemClaim(itemId)` | เลิกผูก | `UNLINK_PURCHASE_ITEM_CLAIM` |

หน้าจอ: ป้ายใบเบิกในแถวรายการ · ส่วน "ใบเบิก" ในหน้าต่างแก้รายการ (ผูก / เลิกผูก) · เมนูการ์ด "ผูกใบเบิกกับหลายรายการ" · หัวการ์ดบอก "ผูกใบเบิกแล้ว N/M รายการ" · หน้าใบเบิก (`/finance/[id]`) แสดงรายการจัดซื้อที่ผูกกับใบนั้น

ฐานข้อมูลที่ยังไม่มีคอลัมน์ `expense_claim_id` (รัน migration รุ่นก่อน): หน้าจัดซื้อขึ้นข้อความ "ยังไม่พร้อมใช้งาน" แบบเดียวกับยังไม่มีตาราง — รัน migration ซ้ำแล้วใช้ได้

## Testing Decisions

- `purchasing-logic.check.ts` — assert กติกาล้วนทุกข้อในตารางข้างบน (รันด้วย tsx แบบ `tracking-logic.check.ts`)
- `scripts/purchasing-flow.check.ts` — รัน server action จริงกับฐานข้อมูลจำลองในหน่วยความจำ (แบบ `scripts/salary-edit-flow.check.ts`): ไม่ล็อกอินถูกปฏิเสธ, สร้างใบผูกงาน/ทั่วไป, สร้างซ้ำได้ใบเดิม, เพิ่มรายการและตรวจขีดจำกัด, เปลี่ยนสถานะและการประทับเวลา, ใบเสร็จครบแล้วแจ้งเตือน, สิทธิ์ลบ, ใช้ชุดสำเร็จรูป, เพดานรูป 4 รูป
- migration ทดสอบกับ postgres 17 ในเครื่อง (รันซ้ำได้, CHECK, unique, RLS, cascade)
- `npx tsc --noEmit` คง 13 error เดิม · eslint 0 error
- ภาพจำลองหน้าจอ (จอกว้าง + 360px, สว่าง + มืด) ตรวจโดยผู้ตรวจ

## Out of Scope

- ส่งยอดจ่ายจริงเข้าเมนูต้นทุนอัตโนมัติ — ของที่พนักงานซื้อแล้วทำใบเบิกถูกนับเป็นต้นทุนจากใบเบิกอยู่แล้ว ส่งอีกทางจะนับซ้ำ ต้องออกแบบเป็นการผูกรายการกับใบเบิก
- ตัดสต๊อก/รับของเข้าคลัง · ใบสั่งซื้อ (PO) เป็นเอกสาร · อนุมัติการซื้อ · ลากเรียงลำดับรายการ · อัปเดตสดหลายคนพร้อมกัน · คู่มือในหน้า /howto · ป้ายในตารางติดตามงาน

## Further Notes

### สิ่งที่ต่างจากแผนตอนลงมือ (2026-09-29)

- ตัวกรองและมุมมองเขียนลง URL ด้วย `window.history.replaceState` ไม่ใช่ `router.replace` — ตัวกรองทำฝั่ง browser ทั้งหมด ถ้านำทางจริง server จะโหลดเช็กลิสต์ทั้งชุดใหม่ทุกครั้งที่กดชิปหรือพิมพ์ค้น · `?past=1` เท่านั้นที่เป็นการนำทางจริง
- แถวรายการสลับเป็นตาราง 8 ช่องตาม **ความกว้างของการ์ด** (container query `@4xl` = 56rem) ไม่ใช่ความกว้างจอ — แถบเมนูซ้ายกินที่จนตารางล้นที่จอขนาดกลาง
- เช็กลิสต์ที่เปิดจากลิงก์ `?list=` แสดงเสมอแม้ตัวกรองหรือ "ซ่อนที่เสร็จแล้ว" จะซ่อน (แจ้งเตือน "ของครบแล้ว" ชี้ไปใบที่เสร็จแล้ว) · เปลี่ยนตัวกรองแล้วเลิกโหมดลิงก์
- การ์ดกางเองเมื่อมีตัวกรองทำงานด้วย (นอกจากลิงก์และรายการด่วน)
- ขนาดรูป 5MB ตรวจ **หลังบีบ** (รูปจากกล้องมือถือเกิน 5MB บ่อย บีบแล้วเหลือไม่ถึง 1MB) · ชนิด จำนวน และไฟล์ว่างตรวจก่อนบีบ · server ตรวจซ้ำทุกข้อ
- กรอบบอร์ดต้องเป็น `relative`: ข้อความ `sr-only` ในการ์ดเป็น `position: absolute` ถ้าไม่มีบรรพบุรุษที่ยึดไว้จะหลุดการตัดขอบของกรอบเลื่อน แล้วทำให้ทั้งหน้าเลื่อนแนวนอนบนมือถือ (เจอจากการตรวจที่ความกว้าง 360px)
- `isAdmin` ของหน้านี้อ่านจาก `profiles.role` ไม่ใช่ cookie `session_role` (cookie นั้นไม่ได้เซ็น)
- ผูกใบเบิก: หน้าต่างผูกหลายรายการมีปุ่ม "เลือกทั้งหมด" (ติ๊กให้เองอาจเกิน 50) · รายการที่ผูกกับใบที่เลือกอยู่แล้วแสดงแบบติ๊กไว้และกดไม่ได้ · เตือนเมื่อรายการที่ติ๊กจะถูกย้ายมาจากใบเบิกอื่น
- ผูกใบเบิก: ผูกใบใหม่แทนใบเดิมแล้ว หน้าใบเบิกใบเดิมถูก revalidate ด้วย และ log เก็บ `replacedClaimIds`
- ผูกใบเบิก: กติกาเข้มกว่า Finance หนึ่งจุด — Finance ให้พนักงานทุกคนเห็นเอกสารที่เกี่ยวกับเงินสดย่อย แต่หน้าจัดซื้อให้เห็นรายละเอียดและผูกได้เฉพาะผู้เบิกกับแอดมินเสมอ (ยังไม่ได้ถามเจ้าของว่าต้องการให้ตรงกันหรือไม่)
- หน้าใบเบิกอ่านรายการที่ผูกด้วย 3 คำถามต่อเนื่อง (รายการ → เช็กลิสต์ → การ์ด CRM) เพื่อแสดงชื่อเช็กลิสต์แบบเดียวกับหน้าจัดซื้อ

### อื่นๆ

- การ์ด CRM ในระบบจริงเกิน 1,000 ใบ (สถานะที่ถือว่าตอบรับแล้วมี accepted, Success, ปิด) ช่องเลือกงานจึงต้องค้นฝั่ง server
- ต้องรัน migration บน production ก่อน deploy — ถ้า deploy ก่อน หน้าจัดซื้อจะขึ้นข้อความว่ายังไม่ได้ติดตั้ง ส่วนอื่นของระบบไม่กระทบ
