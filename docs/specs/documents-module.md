# Spec: โมดูล "เอกสาร" (Document Control) — `/documents`

สถานะ: `ready-for-agent`
ที่มา: `docs/document-control-system-spec.md` (v1.0) ผ่านการ grill 3 รอบ 2026-08-27 — เอกสารนี้คือข้อสรุปที่ตกลงแล้ว ใช้แทน spec ต้นฉบับในส่วนที่ขัดกัน

---

## Problem Statement

ทีมออกเอกสารธุรกิจ (ใบเสนอราคา ใบแจ้งหนี้ ใบเสร็จ ฯลฯ) และเอกสาร HR (ใบสมัครงาน ใบลาออก) นอกระบบ — ต่างคนต่างก๊อปไฟล์เก่ามาแก้ เลขที่เอกสารเป็นข้อความพิมพ์มือ (`crm_leads.quotation_ref`) ทำให้เลขซ้ำ/ข้าม ตรวจย้อนหลังไม่ได้ ไม่มีหลักฐานว่าใครอนุมัติเมื่อไร และแบรนด์ทั้ง 3 (แต่ละแบรนด์เป็นนิติบุคคลแยกกัน) ใช้หัวกระดาษ/เงื่อนไขไม่ตรงกัน

ระบบที่มีอยู่ (ใบสำคัญจ่ายในโมดูลการเงิน) รันเลขด้วย `count+1` ซึ่งซ้ำได้เมื่อกดพร้อมกันและเลขกลับมาใช้ใหม่เมื่อลบ — ห้ามใช้วิธีนี้กับเอกสารภาษี

## Solution

โมดูลใหม่ "เอกสาร" ในเมนูข้างของแอปเดิม ผู้ใช้เลือกแบรนด์ + ประเภท กรอกฟอร์มเดียวที่ปรับส่วนตามประเภท ได้เลขร่างทันที ส่งขออนุมัติ admin กดอนุมัติแล้วระบบออกเลขจริงในธุรกรรมที่ล็อกตัวนับ เปิด PDF ได้ทันทีด้วยหัวกระดาษ/เงื่อนไข/ลายเซ็นตามแบรนด์ เอกสารที่ออกเลขแล้วแก้ไม่ได้และลบไม่ได้ (ยกเลิกได้เฉพาะ VOID พร้อมเหตุผล เลขไม่ถูกใช้ซ้ำ) ทุกการเปลี่ยนสถานะมี log และแจ้งเตือนในแอป admin มีหน้าตั้งค่าแบรนด์/ตัวนับ/แม่แบบ, หน้ารออนุมัติ, แดชบอร์ด และรายงานตรวจความต่อเนื่องของเลข

## User Stories

### สร้างและแก้ไขร่าง
1. ในฐานะผู้ใช้ทั่วไป ฉันต้องการกด "สร้างเอกสาร" แล้วเลือกแบรนด์และประเภทจาก 13 ประเภท เพื่อเริ่มเอกสารใหม่ได้ในไม่กี่คลิก
2. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเห็นเฉพาะแบรนด์ที่เปิดใช้งาน และไม่เห็นประเภท "ใบกำกับภาษี" สำหรับแบรนด์ที่ไม่ได้จด VAT เพื่อไม่ออกเอกสารผิดกฎหมาย
3. ในฐานะผู้ใช้ทั่วไป ฉันต้องการให้ระบบให้เลขร่าง `DRAFT-NNNN` ทันทีที่สร้าง เพื่อใช้อ้างอิงระหว่างที่ยังไม่อนุมัติโดยไม่กินเลขจริง
4. ในฐานะผู้ใช้ทั่วไป ฉันต้องการฟอร์มที่แสดงเฉพาะส่วนที่เกี่ยวกับประเภทที่เลือก (เช่น วันหมดอายุเฉพาะใบเสนอราคา, ไม่มีตารางรายการในบันทึกข้อความ) เพื่อไม่สับสน
5. ในฐานะผู้ใช้ทั่วไป ฉันต้องการกรอกข้อมูลคู่สัญญา (ชื่อ, บริษัท, เลขผู้เสียภาษี, ที่อยู่, เบอร์, อีเมล) ในเอกสารโดยตรง เพื่อให้เอกสารเป็น snapshot ที่ไม่เปลี่ยนตามข้อมูลลูกค้าภายหลัง
6. ในฐานะผู้ใช้ทั่วไป ฉันต้องการพิมพ์ชื่อลูกค้าแล้วเลือกจากรายการที่เคยออกเอกสารให้ เพื่อให้ระบบเติมบริษัท/เลขภาษี/ที่อยู่ให้โดยไม่ต้องพิมพ์ซ้ำ
7. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเพิ่ม/ลบ/เรียงลำดับรายการ (รายละเอียด, จำนวน, หน่วย, ราคาต่อหน่วย, ส่วนลดต่อรายการ) และเห็นยอดรวมคำนวณสด เพื่อลดความผิดพลาดในการคิดเลข
8. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเลือกโหมด VAT (ไม่มี / แยกนอก 7% / รวมใน 7%) และอัตราหัก ณ ที่จ่าย (0/1/2/3/5%) โดยมีค่าเริ่มต้นจากแบรนด์ เพื่อให้ยอดสุทธิถูกต้องตามที่ลูกค้าจะจ่ายจริง
9. ในฐานะผู้ใช้ทั่วไป ฉันต้องการให้ใบแจ้งหนี้อ้างอิงใบเสนอราคา ใบเสร็จอ้างอิงใบแจ้งหนี้ ใบส่งมอบอ้างอิงใบสั่งจ้าง โดยเลือกจากเอกสารที่ออกเลขแล้วในระบบ เพื่อให้สายเอกสารเชื่อมกันได้
10. ในฐานะผู้ใช้ทั่วไป ฉันต้องการให้ใบลดหนี้บังคับอ้างอิงเอกสารต้นทางและใส่เหตุผล เพื่อให้เป็นไปตามข้อกำหนดทางบัญชี
11. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเขียนเนื้อหาสัญญาจ้าง / บันทึกข้อความ / ประวัติผู้สมัคร เป็น rich text เพื่อจัดรูปแบบย่อหน้าและหัวข้อได้
12. ในฐานะผู้ใช้ทั่วไป ฉันต้องการกรอกใบสมัครงาน/ใบสมัครฝึกงานแทนผู้สมัคร (ข้อมูลบุคคล, ตำแหน่ง, เงินเดือนที่ต้องการ, วันเริ่มงานได้, สถาบัน/สาขา/ช่วงฝึกงาน/อาจารย์ที่ปรึกษา) เพื่อเก็บเป็นเอกสารมีเลขในระบบ
13. ในฐานะผู้ใช้ทั่วไป ฉันต้องการกรอกใบลาออก (ชื่อ, ตำแหน่ง, แผนก, วันทำงานสุดท้าย, เหตุผล) แล้วส่งให้ admin อนุมัติ เพื่อมีหลักฐานการรับทราบ
14. ในฐานะผู้ใช้ทั่วไป ฉันต้องการบันทึกร่างแล้วกลับมาแก้ทีหลังได้ไม่จำกัดครั้ง เพื่อไม่ต้องทำให้เสร็จในครั้งเดียว
15. ในฐานะผู้ใช้ทั่วไป ฉันต้องการลบร่างของตัวเองได้ เพราะยังไม่มีเลขจริงและไม่กระทบใคร
16. ในฐานะผู้ใช้ทั่วไป ฉันต้องการกด "คัดลอกเป็นร่างใหม่" จากเอกสารใดก็ได้ เพื่อออกเอกสารคล้ายเดิมหรือแก้เอกสารที่ VOID ไปแล้วโดยไม่พิมพ์ใหม่
17. ในฐานะผู้ใช้ทั่วไป ฉันต้องการให้ระบบตรวจความครบถ้วนก่อนส่ง (คู่สัญญา, อย่างน้อย 1 รายการสำหรับประเภทที่มียอด, ฟิลด์บังคับเฉพาะประเภท) และบอกชัดว่าขาดอะไร เพื่อไม่ถูกตีกลับด้วยเรื่องเล็ก

### ขออนุมัติและออกเลข
18. ในฐานะผู้ใช้ทั่วไป ฉันต้องการกด "ส่งขออนุมัติ" แล้วเอกสารเปลี่ยนเป็น "รออนุมัติ" และแก้ไขไม่ได้จนกว่าจะถูกตีกลับ เพื่อให้ admin ตรวจฉบับที่นิ่งแล้ว
19. ในฐานะผู้ใช้ทั่วไป ฉันต้องการให้ประเภทที่ไม่ต้องอนุมัติ (ใบส่งมอบ, บันทึกข้อความ, ใบสมัครงาน, ใบสมัครฝึกงาน) กด "ออกเอกสาร" แล้วได้เลขจริงทันที เพื่อไม่ต้องรอ admin กับเอกสารที่ไม่มีผลทางการเงิน
20. ในฐานะ admin ฉันต้องการหน้า "รออนุมัติ" ที่แสดงทุกใบที่ค้าง พร้อมประเภท, แบรนด์, ผู้ขอ, ยอด, เวลาที่ส่ง เพื่อจัดการได้ในที่เดียว
21. ในฐานะ admin ฉันต้องการเห็นป้ายแดง "ค้างเกิน 24 ชม." และตัวเลข badge บนเมนู เพื่อรู้ว่ามีงานค้างโดยไม่ต้องเปิดหน้า
22. ในฐานะ admin ฉันต้องการกด "อนุมัติ" พร้อมใส่ความเห็น (ไม่บังคับ) แล้วระบบออกเลขจริงในทันที เพื่อให้ผู้ขอเอาไปใช้ได้เลย
23. ในฐานะ admin ฉันต้องการกด "ตีกลับ" โดย**บังคับ**ใส่เหตุผล เพื่อให้ผู้ขอรู้ว่าต้องแก้อะไร
24. ในฐานะ admin ฉันต้องการอนุมัติเอกสารที่ตัวเองสร้างได้ (กรณีมี admin คนเดียว) โดยระบบติดป้าย "อนุมัติด้วยตนเอง" และบันทึกเป็นข้อยกเว้นใน log เพื่อไม่ติดตายแต่ยังตรวจสอบได้
25. ในฐานะเจ้าของกิจการ ฉันต้องการให้เลขที่เอกสารไม่ซ้ำแม้ admin 2 คนกดอนุมัติเอกสาร 2 ใบพร้อมกัน เพื่อให้เอกสารภาษีถูกต้อง
26. ในฐานะเจ้าของกิจการ ฉันต้องการให้ใบกำกับภาษี/ใบเสร็จ/ใบลดหนี้รันเลขต่อเนื่องทั้งปีโดยไม่รีเซ็ตรายเดือน ตามกฎกรมสรรพากร
27. ในฐานะเจ้าของกิจการ ฉันต้องการให้เอกสารที่ยังไม่อนุมัติไม่แสดงเลขจริงที่ไหนเลย (แสดงเลขร่างแทน) เพื่อไม่ให้มีเอกสารเลขจริงหลุดไปก่อนอนุมัติ
28. ในฐานะผู้ใช้ทั่วไป ฉันต้องการได้รับแจ้งเตือนในแอปเมื่อเอกสารถูกอนุมัติหรือตีกลับ (มีประเภท, ชื่อคู่สัญญา, ยอด, และลิงก์เปิดเอกสาร) เพื่อไม่ต้องเข้ามาเช็คเอง
29. ในฐานะ admin ฉันต้องการได้รับแจ้งเตือนในแอปเมื่อมีเอกสารใหม่รออนุมัติ เพื่ออนุมัติได้ภายใน 1 วันทำการ
30. ในฐานะผู้ใช้ทั่วไป ฉันต้องการให้เอกสารที่ถูกตีกลับกลับเป็นร่างพร้อมแสดงเหตุผลเด่นชัดด้านบน เพื่อแก้แล้วส่งใหม่ได้ทันที

### หลังออกเลข
31. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเปิด/ดาวน์โหลด PDF ของเอกสารที่ออกเลขแล้ว ที่แสดงเลขที่, โลโก้และข้อมูลแบรนด์, คู่สัญญา, รายการ, ยอดเป็นตัวเลขและตัวอักษรไทย, ชื่อผู้อนุมัติ, วันที่อนุมัติ (พ.ศ.) และรูปลายเซ็นผู้อนุมัติถ้ามี เพื่อส่งให้ลูกค้าได้ทันที
32. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเปิด PDF ตัวอย่างของร่างได้ (มีลายน้ำ "ร่าง" และเลขร่างแทนเลขจริง) เพื่อตรวจหน้าตาก่อนส่งอนุมัติ
33. ในฐานะผู้สร้างเอกสาร ฉันต้องการกด "ส่งให้ลูกค้าแล้ว" และ "ปิดงาน" เพื่อติดตามสถานะโดยไม่แตะเนื้อหา
34. ในฐานะเจ้าของกิจการ ฉันต้องการให้เอกสารที่ออกเลขแล้ว**แก้เนื้อหาไม่ได้และลบไม่ได้แม้เป็น admin** โดยถูกปฏิเสธที่ฐานข้อมูล ไม่ใช่แค่ซ่อนปุ่ม เพื่อให้ตรวจสอบย้อนหลังเชื่อถือได้
35. ในฐานะ admin ฉันต้องการ VOID เอกสารที่ออกเลขแล้วโดยบังคับใส่เหตุผล เพื่อยกเลิกเอกสารผิดโดยเลขนั้นถูกใช้ไปตลอด
36. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเห็นเอกสาร VOID ในรายการด้วยสถานะชัดเจน (และ PDF มีตราประทับ "ยกเลิก") เพื่อไม่เอาไปใช้ผิด
37. ในฐานะ admin ฉันต้องการอัปโหลดรูปลายเซ็นของตัวเองในหน้าโปรไฟล์ (ระบบย่อขนาดให้) เพื่อให้ PDF มีลายเซ็นโดยไม่ต้องพิมพ์แล้วเซ็นมือ

### ค้นหาและติดตาม
38. ในฐานะผู้ใช้ทั่วไป ฉันต้องการค้นหาเอกสารด้วยเลขที่หรือชื่อคู่สัญญา และกรองตามแบรนด์/ประเภท/สถานะ/เดือน เพื่อหาเอกสารย้อนหลังได้ใน 30 วินาที
39. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเห็นเอกสารที่ออกเลขแล้วของทุกคนในทีม แต่เห็นร่างเฉพาะของตัวเอง เพื่ออ้างอิงงานของเพื่อนร่วมทีมได้โดยไม่เห็นงานที่ยังไม่เสร็จของคนอื่น
40. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเห็นประวัติของเอกสารแต่ละใบ (ใครสร้าง/ส่ง/อนุมัติ/ตีกลับ/VOID เมื่อไร พร้อมเหตุผล) ในหน้าเอกสารนั้น เพื่อรู้ที่มาที่ไปโดยไม่ต้องถาม
41. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเห็นสายเอกสารที่เกี่ยวข้อง (ใบเสนอราคา → ใบแจ้งหนี้ → ใบเสร็จ) ในหน้าเอกสาร เพื่อตามงานลูกค้ารายเดียวได้ครบ
42. ในฐานะ admin ฉันต้องการแดชบอร์ดที่แสดงจำนวนค้างอนุมัติ, ค้างเกิน 24 ชม., ออกเดือนนี้, ยอดรวมตามประเภท, กราฟตามสถานะ และเวลาเฉลี่ยจากส่งถึงอนุมัติ เพื่อเห็นภาพรวมและคอขวด
43. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเห็นแดชบอร์ดเดียวกันแต่นับเฉพาะเอกสารของตัวเอง เพื่อรู้สถานะงานของตัวเอง
44. ในฐานะ admin ฉันต้องการรายงานตรวจความต่อเนื่องของเลข เลือกแบรนด์/ประเภท/ช่วง แล้วเห็นเลขที่ออก, เลขที่หาย (แดง), เลข VOID (เทา) เพื่อตรวจก่อนส่งบัญชีทุกเดือน

### ตั้งค่า (admin)
45. ในฐานะ admin ฉันต้องการเพิ่มแบรนด์ใหม่ (รหัส 3 ตัว, ชื่อไทย/อังกฤษ, ที่อยู่ออกเอกสาร, เลขผู้เสียภาษี, สาขา, เบอร์, อีเมล, เว็บไซต์, โลโก้, จด VAT, เปิด/ปิด) เพื่อรองรับนิติบุคคลใหม่โดยไม่ต้องแก้โค้ด
46. ในฐานะ admin ฉันต้องการให้รหัสแบรนด์ล็อกแก้ไม่ได้หลังออกเลขใบแรก เพื่อไม่ให้เลขเก่า-ใหม่ปนกัน
47. ในฐานะ admin ฉันต้องการเห็นและตั้งค่า "เลขล่าสุด" ของแต่ละชุดตัวนับ (แบรนด์ × ประเภท × งวด) เพื่อรันต่อจากเลขเดิมได้เมื่อจำเป็น
48. ในฐานะ admin ฉันต้องการแก้แม่แบบต่อแบรนด์ × ประเภท (ชื่อหัวเอกสาร, เงื่อนไข/หมายเหตุมาตรฐาน, ข้อความท้ายกระดาษ, ป้ายช่องลงนาม 2 ช่อง, ข้อมูลการชำระเงินสำหรับ QT/IV) เพื่อให้ทุกใบของแบรนด์นั้นหน้าตาเหมือนกัน
49. ในฐานะ admin ฉันต้องการให้ทุกครั้งที่บันทึกแม่แบบเป็นเวอร์ชันใหม่ที่ใช้งานทันที มีประวัติ และกด "ใช้เวอร์ชันนี้" ย้อนกลับได้ เพื่อแก้ผิดแล้วกู้คืนได้
50. ในฐานะ admin ฉันต้องการกด preview PDF ตัวอย่างของแม่แบบก่อนบันทึก เพื่อเห็นผลจริง
51. ในฐานะผู้ตรวจสอบบัญชี ฉันต้องการให้เอกสารทุกใบบันทึกว่าใช้แม่แบบเวอร์ชันไหนตอนออกเลข เพื่อให้ PDF ที่เปิดย้อนหลังตรงกับที่ส่งลูกค้าไปแม้แม่แบบเปลี่ยนภายหลัง
52. ในฐานะ admin ฉันต้องการเปิด/ปิดสิทธิ์โมดูล "เอกสาร" ให้ผู้ใช้แต่ละคนจากหน้าจัดการผู้ใช้เดิม เพื่อควบคุมว่าใครออกเอกสารได้
53. ในฐานะผู้ใช้ทั่วไป ฉันต้องการเห็นรายการ "มีอะไรใหม่" อธิบายโมดูลเอกสารเมื่อ ship เพื่อรู้ว่าใช้อย่างไร

## Implementation Decisions

### โมดูลและเส้นทาง
- โมดูลใหม่ key `documents` ที่ `/documents` — เพิ่มทั้งใน nav config (กลุ่ม "เอกสาร" ไอคอน FileText ถัดจาก finance) และในตาราง MODULE_ROUTES ของ proxy เพื่อบังคับสิทธิ์จริง ผู้ใช้ต้องถูกเปิด module `documents` จึงเห็น/เข้าได้
- เมนูย่อย: รายการเอกสาร `/documents` · รออนุมัติ `/documents/approvals` (adminOnly, badge จำนวนค้าง) · แดชบอร์ด `/documents/dashboard` · รายงานเลขต่อเนื่อง `/documents/reports` (adminOnly) · ตั้งค่า `/documents/settings` (adminOnly: แท็บ แบรนด์ · ตัวนับ · แม่แบบ)
- หน้าเสริม: `/documents/new` (เลือกแบรนด์+ประเภท → ฟอร์ม), `/documents/[id]` (ดู/แก้ร่าง/อนุมัติ/PDF/ประวัติ/คัดลอก)
- ตาม pattern เดิม: `page.tsx` (server, ใช้ `requireAuth()` ไม่ใช่อ่าน cookie `session_role` ตรง) + `*-view.tsx` (client) + `actions.ts` ของโมดูล; หน้า adminOnly ตรวจ role ใน page.tsx เพิ่มจาก proxy
- PDF: route handler ใหม่ `/api/pdf/document/[id]` (nodejs runtime, `requireAuth`, render สดจาก DB ทุกครั้ง ไม่เก็บไฟล์) + renderer react-pdf ใหม่ที่ใช้ฟอนต์ THSarabunNew, ตัวเลขเป็นบาทไทย และ helper คำนวณ VAT/WHT ที่มีอยู่ในโมดูลการเงิน (ย้ายออกมาเป็น helper กลางถ้าจำเป็น)

### เลขที่เอกสาร
- รูปแบบเดียวทั้งระบบ `BRAND-TYPE-YYMM-NNNN` (ค.ศ. 2 หลัก) — ตัวนับรายปี (TX/RC/CN) ยังแสดง YYMM ของเดือนที่ออกแต่เลขวิ่งต่อข้ามเดือน (`MIP-TX-2608-0015` → `MIP-TX-2609-0016`) รีเซ็ต 1 ม.ค.
- ตาราง `doc_counters` key = (brand_code, doc_type, period) โดย period = `YYMM` สำหรับรายเดือน, `YY` สำหรับรายปี; เก็บ last_number, updated_at, updated_by; admin แก้ last_number ได้ในหน้าตั้งค่า
- ร่างใช้ `DRAFT-NNNN` จากตัวนับกลางแยก (period = `'draft'`)
- ออกเลขด้วย Postgres function `issue_document_number(doc_id, actor)` ภายใน transaction: `SELECT … FOR UPDATE` บน `doc_counters` (upsert ถ้ายังไม่มีแถว) → เพิ่มเลข → เขียน `doc_no`, `issued_at`, `approved_by/at`, `template_version_id` → insert `document_logs` — ทั้งหมดใน function เดียว action เรียกผ่าน `rpc`
- ทุกแบรนด์เป็นนิติบุคคลแยก → เอกสารภาษีแยกชุดตามแบรนด์ได้ตรงตัว ไม่ต้องมีชั้น "นิติบุคคล"

### State machine (lowercase ตาม convention repo)
```
draft ──submit──► pending_approval ──approve──► issued ──mark_sent──► sent ──close──► closed
  ▲                     │                        │                     │
  └────────reject───────┘                        └────────void─────────┴──void──► void
draft ──issue (ประเภทไม่ต้องอนุมัติ)──► issued
draft ──delete──► (หายจากระบบ — เฉพาะ status draft/ยังไม่มี doc_no)
```
- `approved` กับ `issued` รวมเป็นขั้นเดียว (PDF render สด ไม่มีขั้น "สร้างไฟล์")
- ไม่มี `pending_review`, `superseded`
- Transition ตรวจในฟังก์ชันเดียว `transition(doc, action, actor)` ฝั่ง server action; ทุก transition เขียน `document_logs` + `logActivity` + notification ที่เกี่ยวข้อง
- **DB trigger** บน `documents`: BEFORE UPDATE ถ้า OLD.doc_no IS NOT NULL ห้ามเปลี่ยนคอลัมน์เนื้อหาใดๆ (อนุญาตเฉพาะ status/void_*/sent_at/closed_at); BEFORE DELETE ถ้า doc_no IS NOT NULL → RAISE — trigger บน `document_items` เช่นกัน (ห้าม insert/update/delete เมื่อเอกสารแม่มีเลขแล้ว) — ครอบคลุม service role ด้วย
- Self-approve: อนุญาต, บันทึก `self_approved = true` ใน log entry และแสดงป้ายบนหน้าเอกสาร

### Schema ใหม่ (migration เดียวใน `supabase/migrations/`)
- `doc_brands`: code (PK, 3 ตัวพิมพ์ใหญ่), name_th, name_en, address, tax_id, branch, phone, email, website, logo_url, vat_registered, default_vat_mode, default_wht_rate, is_active, sort_order — code ล็อกเมื่อมี documents ที่ doc_no ไม่ว่างอ้างถึง (ตรวจใน action)
- `doc_counters`: (brand_code, doc_type, period) PK, last_number, updated_at, updated_by
- `doc_templates`: id, brand_code, doc_type, version (int วิ่งต่อ brand×type), title, terms (HTML), footer, signer_label_1, signer_label_2, payment_info, is_active, created_by, created_at — เพียง 1 แถว is_active ต่อ brand×type (partial unique index)
- `documents`: id, draft_no, doc_no (unique, nullable), brand_code → doc_brands, doc_type, status (CHECK), template_version_id → doc_templates, party_* ชุด, doc_date, due_date/expiry_date ใน meta, meta JSONB, vat_mode, wht_rate, subtotal, discount_total, vat_amount, wht_amount, total, net_payable, currency default 'THB', ref_document_id → documents (nullable), notes, created_by, submitted_at, approved_by, approved_at, issued_at, rejected_reason, void_reason, void_by, void_at, sent_at, closed_at, created_at, updated_at
- `document_items`: id, document_id (CASCADE เฉพาะเมื่อยังไม่มีเลข — บังคับด้วย trigger), line_no, description, quantity, unit, unit_price, discount, amount
- `document_logs`: id, document_id, action, from_status, to_status, changed_by, note, self_approved, created_at (ตาม pattern `expense_claim_logs`)
- `profiles.signature_url` (nullable)
- Storage bucket ใหม่ `doc-assets` (โลโก้แบรนด์); ลายเซ็นเก็บใน `avatars` ที่มีอยู่
- ขยาย CHECK ของ `notifications.type` / `reference_type` ให้รองรับ `doc_*` / `document`
- RLS: เปิดตาม pattern repo (permissive to authenticated) — สิทธิ์จริงบังคับใน server actions + trigger

### แม่แบบ
- แก้ได้ต่อ brand × type: title, terms (TipTap → HTML → แปลงเป็น react-pdf ด้วย parser ง่ายๆ รองรับ p/strong/em/ul/ol/br เท่านั้น), footer, signer labels, payment_info (แสดงเฉพาะ QT/IV)

- ไม่มีแม่แบบสำหรับ brand×type → ใช้ค่า default จาก config `DOC_TYPES`

### PDF
- Layout react-pdf 1 ชุดที่ปรับส่วนตามกลุ่ม: การเงิน (ตารางรายการ+ยอด), รายการอย่างเดียว (DN), จดหมาย (MM/CT/RS/JA/IA เนื้อหา rich text + ข้อมูลบุคคล)
- แสดงเลขที่ (หรือเลขร่าง + ลายน้ำ "ร่าง" ถ้ายังไม่ออกเลข; ตรา "ยกเลิก" ถ้า void), โลโก้/ข้อมูลแบรนด์, คู่สัญญา, วันที่ พ.ศ., ยอดตัวอักษรไทย, ช่องลงนาม 2 ช่อง (ช่องผู้อนุมัติ = รูปลายเซ็นถ้ามี + ชื่อ + วันที่อนุมัติ)
- ลายเซ็น: อัปโหลดในหน้าโปรไฟล์ PNG/JPG ย่อฝั่ง client ให้ด้านยาวสุด 400px ก่อนอัปโหลด (ใช้ `compressImage` เดิมโดยกำหนด max ใหม่)

**Seam ที่ใช้ทดสอบ (seam เดียว): Postgres function + trigger ผ่าน service client** — เป็นจุดสูงสุดที่ครอบคลุมกติกาเหล็กทั้งหมดของ spec โดยไม่ต้องพึ่ง UI และไม่ต้อง mock อะไร (server action เป็นแค่ชั้นบางๆ ที่เรียก rpc + ตรวจ role)

script `scripts/doc-control-check.ts` (รันด้วย `tsx` กับ DB จริง ใช้แบรนด์ทดสอบ `ZZT` แล้วลบทิ้งตอนจบ) ตรวจเฉพาะพฤติกรรมภายนอก:
1. เรียก `issue_document_number` พร้อมกัน 20 ครั้ง (Promise.all) กับเอกสาร 20 ใบ → ได้เลข 0001–0020 ครบ ไม่ซ้ำ ไม่ข้าม (AC1)
2. เอกสาร `pending_approval` ไม่มี `doc_no` (AC2)
3. DELETE เอกสารที่มี doc_no → error จาก DB แม้ใช้ service role (AC3)
4. UPDATE `total`/`party_name`/`document_items` ของเอกสารที่มี doc_no → error; UPDATE `status` เป็น `void` → ผ่าน (AC4)
5. ตีกลับด้วยเหตุผลว่าง → action คืน `{ error }` (AC5)
6. TX ออก 2 ใบคนละเดือนในปีเดียวกัน → เลขต่อเนื่อง; RC ข้ามปี → รีเซ็ต (§5.2)
7. VOID แล้วออกใบใหม่ → ได้เลขถัดไป ไม่ใช่เลขที่ VOID (§5.3 ข้อ 2)
8. รายงานเลขต่อเนื่อง: จงใจ UPDATE last_number กระโดด → รายงานแสดงเลขหาย (AC9)
9. ทุก transition มี `document_logs` 1 แถว พร้อม changed_by (AC10)

Prior art: `scripts/seed-advance-test.ts` (script ทดสอบต่อ DB จริงด้วย service client)

สิ่งที่ไม่ทดสอบอัตโนมัติ: หน้าตา PDF (ตรวจด้วยตา), UI

## Out of Scope

- Revision (`REV.02`) / สถานะ `superseded` — ใช้ VOID + คัดลอกเป็นร่างใหม่แทน (เก็บ `ref_document_id` ไว้ให้เพิ่มทีหลังได้)
- ขั้นผู้ตรวจ (reviewer) แยกจากผู้อนุมัติ, เส้นทางอนุมัติตามวงเงิน (`approval_rules`), delegation, escalate — ระบบมี role ชั้นเดียว
- เตือนซ้ำ 24/48 ชม. อัตโนมัติ (ไม่มี cron), LINE Notify/Messaging, อีเมล
- Workflow อนุมัติแม่แบบ, template editor แบบ placeholder เต็มรูปแบบ, อัปโหลดไฟล์ Google Docs
- ตาราง customers / ผูก `crm_leads` / เพิ่มคอลัมน์ให้ CRM
- เก็บไฟล์ PDF ลง storage, ลิงก์สาธารณะให้ลูกค้าหรือผู้สมัครกรอก/ดู/ยอมรับเอง
- ลายเซ็นดิจิทัลตามกฎหมาย, e-Tax Invoice, ส่งออกให้สำนักงานบัญชี
- นำเข้าเอกสารย้อนหลัง — เริ่ม 0001 ในเดือนที่เปิดใช้
- สกุลเงินอื่นนอกจาก THB, ส่วนลดท้ายบิล (มีเฉพาะต่อรายการ)
- backup อัตโนมัติ (เป็นเรื่องระดับ Supabase project)

## Further Notes

- รหัสแบรนด์เริ่มต้นที่ seed: MIP (M Image), PPB (Prince Photo Booth), PLT (PhotoLand) — เจ้าของต้องกรอกที่อยู่/เลขผู้เสียภาษี/จด VAT ของแต่ละนิติบุคคลในหน้าตั้งค่าก่อนออกเอกสารจริง; ระบบต้องบล็อกการส่งอนุมัติถ้าแบรนด์ยังไม่มีเลขผู้เสียภาษี/ที่อยู่ (สำหรับประเภทการเงิน)
- อย่านำ pattern `count+1` ของ `expense_claims`/`check-in` มาใช้ — ถ้าจะแก้ของเดิมให้ใช้ `doc_counters` ตัวเดียวกันเป็นงานแยกทีหลัง
- ห้ามเปลี่ยนรหัสประเภท/แบรนด์หลัง deploy — spec ต้นฉบับ §4, §13
- ทุก path อยู่ใต้ auth (proxy) — ไม่มี route สาธารณะ
- ลำดับงานที่แนะนำ: migration + function/trigger + check script → actions + transition → หน้า settings (ต้องมีแบรนด์ก่อนสร้างเอกสาร) → new/[id]/list → approvals → PDF → dashboard/reports → nav/proxy/notifications/whats-new → `tsc --noEmit`
