# สเปกโปรเจกต์: ระบบควบคุมเอกสาร (Document Control System)

ระบบรันเลขที่เอกสาร + คลัง Template + Workflow อนุมัติ

เวอร์ชันเอกสาร: 1.0
สถานะ: ร่างเพื่อเริ่มโปรเจกต์

---

## 1. ภาพรวมและเป้าหมาย

ระบบกลางสำหรับออกเอกสารธุรกิจทุกประเภท โดยควบคุม 3 เรื่องพร้อมกัน

1. **เลขที่เอกสาร** ต้องไม่ซ้ำ ไม่ข้าม และตรวจสอบย้อนหลังได้
2. **แม่แบบเอกสาร** ต้องเป็นเวอร์ชันเดียวกันทั้งบริษัท ไม่ใช่ต่างคนต่างก๊อปไฟล์เก่ามาแก้
3. **การอนุมัติ** ต้องมีหลักฐานว่าใครอนุมัติ เมื่อไร ด้วยเงื่อนไขอะไร

### ตัวชี้วัดความสำเร็จ

| ตัวชี้วัด | เป้าหมาย |
|---|---|
| เลขที่เอกสารซ้ำหรือข้าม | 0 รายการต่อเดือน |
| เวลาตั้งแต่ขออนุมัติจนอนุมัติเสร็จ | ไม่เกิน 1 วันทำการ |
| เอกสารที่ออกนอกระบบ (ทำมือ) | ไม่เกิน 5% ภายในเดือนที่ 3 |
| เวลาค้นหาเอกสารย้อนหลัง | ไม่เกิน 30 วินาที |

## 2. ขอบเขต

### อยู่ในขอบเขต (Phase 1-2)

- ออกเลขที่เอกสารอัตโนมัติแยกตามแบรนด์ ประเภท และปี
- คลัง Template พร้อมระบบเวอร์ชัน
- Workflow อนุมัติหลายระดับตามเงื่อนไข
- สร้างไฟล์ PDF และจัดเก็บอัตโนมัติ
- ระบบค้นหาและ audit log
- แจ้งเตือนผ่าน LINE และอีเมล

### อยู่นอกขอบเขต (พิจารณาภายหลัง)

- ระบบบัญชีเต็มรูปแบบและการปิดงบ
- การเชื่อมต่อกับกรมสรรพากร (e-Tax Invoice)
- ระบบสต็อกและคลังสินค้า
- ลายเซ็นดิจิทัลแบบมีผลผูกพันทางกฎหมาย (Digital Signature ตาม พ.ร.บ.) — Phase 1 ใช้เพียงบันทึกการอนุมัติในระบบ

## 3. ผู้ใช้งานและสิทธิ์

| บทบาท | สิทธิ์หลัก |
|---|---|
| Requester (ผู้ขอออกเอกสาร) | สร้างร่าง แก้ไขร่างของตัวเอง ส่งขออนุมัติ ดูเอกสารของตัวเอง |
| Reviewer (ผู้ตรวจ) | ตรวจสอบความถูกต้อง ตีกลับพร้อมเหตุผล ส่งต่อผู้อนุมัติ |
| Approver (ผู้อนุมัติ) | อนุมัติหรือไม่อนุมัติ ดูเอกสารในสายงานตัวเอง |
| Document Controller | จัดการ Template จัดการชุดเลข ยกเลิกเอกสาร แก้ไขข้อมูลหลัก |
| Admin | จัดการผู้ใช้ สิทธิ์ กติกา workflow และดู audit log ทั้งหมด |
| Viewer | ดูอย่างเดียว ไม่แก้ไข (เช่น ทีมบัญชีภายนอก) |

**กติกาสิทธิ์:** ผู้สร้างเอกสารต้องไม่ใช่ผู้อนุมัติเอกสารฉบับเดียวกัน (Segregation of Duties) หากจำเป็นต้องอนุมัติเอง ระบบต้องบันทึกเป็นข้อยกเว้นและแจ้งเตือน Admin

## 4. ประเภทเอกสารและรหัส

ปรับรายการนี้ตามที่ใช้จริง แต่รหัสต้องนิ่งตั้งแต่วันแรก เพราะเปลี่ยนทีหลังจะกระทบเอกสารเก่าทั้งหมด

| ประเภทเอกสาร | รหัส | ต้องอนุมัติ | หมายเหตุ |
|---|---|---|---|
| ใบเสนอราคา | QT | ใช่ (ตามวงเงิน) | มีวันหมดอายุ |
| ใบสั่งจ้าง / ใบยืนยันงาน | JO | ใช่ | ผูกกับวันงานและทีมงาน |
| ใบแจ้งหนี้ | IV | ใช่ | ผูกกับ QT |
| ใบกำกับภาษี | TX | ใช่ | **เลขต้องเรียงต่อเนื่อง ห้ามข้าม** |
| ใบเสร็จรับเงิน | RC | ใช่ | **เลขต้องเรียงต่อเนื่อง ห้ามข้าม** |
| ใบลดหนี้ | CN | ใช่ (ระดับสูง) | ต้องอ้างอิงเอกสารต้นทาง |
| ใบสั่งซื้อ | PO | ใช่ (ตามวงเงิน) | |
| สัญญาจ้าง | CT | ใช่ (ระดับสูง) | มีระบบ revision |
| ใบส่งมอบงาน | DN | ไม่ | |
| เอกสารภายใน / บันทึกข้อความ | MM | ไม่ | |

**ข้อควรระวังเรื่องภาษี:** เอกสารกลุ่ม TX, RC, CN ต้องออกในนามนิติบุคคลที่จดทะเบียนภาษี ไม่ใช่แยกตามแบรนด์ทางการตลาด หากทุกแบรนด์อยู่ใต้นิติบุคคลเดียวกัน ให้ใช้ชุดเลขเดียวรวมกัน และแยกแบรนด์ด้วยคอลัมน์ข้อมูลแทน ไม่ใช่แยก prefix

## 5. กติกาการรันเลขที่เอกสาร

### 5.1 รูปแบบเลข

```
[BRAND]-[TYPE]-[YYMM]-[NNNN]

ตัวอย่าง
MIP-QT-2608-0001    ใบเสนอราคาแบรนด์ M Image ลำดับที่ 1 ของเดือน ส.ค. 2026
PPB-JO-2608-0014    ใบสั่งจ้างแบรนด์ Prince Photo Booth
PLT-IV-2609-0003    ใบแจ้งหนี้แบรนด์ PhotoLand
```

| ส่วน | ความหมาย | กติกา |
|---|---|---|
| BRAND | รหัสแบรนด์ 3 ตัวอักษร | MIP / PPB / PLT (กำหนดในตารางข้อมูลหลัก) |
| TYPE | รหัสประเภทเอกสาร | ตามตารางข้อ 4 |
| YYMM | ปี ค.ศ. 2 หลัก + เดือน 2 หลัก | ใช้ ค.ศ. เพื่อเรียงลำดับได้ถูกต้อง |
| NNNN | เลขลำดับ 4 หลัก | เติมศูนย์หน้า เช่น 0001 |

### 5.2 การรีเซ็ตตัวนับ

- เอกสารทั่วไป: รีเซ็ตทุกเดือน
- เอกสารภาษี (TX, RC, CN): **ไม่รีเซ็ตรายเดือน** ให้รันต่อเนื่องทั้งปีภาษี และรีเซ็ตต้นปีภาษีเท่านั้น
- ตารางตัวนับต้องเก็บแยกรายการ: brand + type + period + last_number

### 5.3 กติกาเหล็ก (ห้ามละเมิด)

1. **ออกเลขจริงตอนอนุมัติเท่านั้น** ระหว่างร่างให้ใช้เลขชั่วคราว `DRAFT-{running}` ที่แยกชุดกันคนละตัวนับ
2. **ห้ามลบเอกสารที่ออกเลขแล้ว** ทำได้แค่เปลี่ยนสถานะเป็น VOID พร้อมเหตุผล เลขนั้นจะถูกใช้ไปตลอด ไม่นำกลับมาใช้ใหม่
3. **ห้ามแก้ไขเอกสารที่ออกเลขแล้ว** ต้องออกเป็น revision ใหม่ (`MIP-QT-2608-0001 REV.02`) หรือออกใบลดหนี้ แล้วแต่ประเภท
4. **ต้องล็อกตัวนับขณะออกเลข** เพื่อกันกรณีผู้ใช้ 2 คนกดอนุมัติพร้อมกันแล้วได้เลขซ้ำ
   - Apps Script: ใช้ `LockService.getScriptLock()` พร้อม timeout 30 วินาที
   - ฐานข้อมูล: ใช้ transaction ร่วมกับ `SELECT ... FOR UPDATE` หรือ sequence ของฐานข้อมูลโดยตรง
5. **ทุกครั้งที่ออกเลข ต้องบันทึก log** ว่าใครออก เมื่อไร ให้เอกสารฉบับไหน

### 5.4 การจัดการเลขข้ามและเลขเสีย

- ระบบต้องมีรายงาน "ตรวจสอบความต่อเนื่องของเลข" รายเดือน แสดงเลขที่หายไปในแต่ละชุด
- ถ้าพบเลขข้าม ต้องมีเอกสารสถานะ VOID รองรับเสมอ ไม่เช่นนั้นถือเป็นข้อผิดพลาดที่ต้องสอบสวน

## 6. สถานะเอกสาร (State Machine)

| สถานะ | ความหมาย | ไปต่อได้ที่ |
|---|---|---|
| DRAFT | ร่าง แก้ไขได้อิสระ ยังไม่มีเลขจริง | PENDING_REVIEW, DELETED |
| PENDING_REVIEW | รอผู้ตรวจ | PENDING_APPROVAL, REJECTED |
| PENDING_APPROVAL | รอผู้อนุมัติ | APPROVED, REJECTED |
| REJECTED | ถูกตีกลับ พร้อมเหตุผล | DRAFT |
| APPROVED | อนุมัติแล้ว **ระบบออกเลขจริงที่จุดนี้** | ISSUED |
| ISSUED | ออกเลขและสร้าง PDF แล้ว ล็อกการแก้ไข | SENT, VOID, SUPERSEDED |
| SENT | ส่งให้ลูกค้าหรือคู่ค้าแล้ว | VOID, SUPERSEDED, CLOSED |
| VOID | ยกเลิก เลขถูกใช้ไปแล้วและจะไม่ถูกใช้ซ้ำ | (สิ้นสุด) |
| SUPERSEDED | ถูกแทนที่ด้วย revision ใหม่ | (สิ้นสุด) |
| CLOSED | จบงาน เช่น ใบแจ้งหนี้ที่ชำระครบแล้ว | (สิ้นสุด) |

**เงื่อนไข:** สถานะ ISSUED ขึ้นไป ห้ามแก้ไขเนื้อหาทุกกรณี ระบบต้องปิดปุ่มแก้ไขในระดับสิทธิ์ ไม่ใช่แค่ซ่อน UI

## 7. Workflow ที่ต้องมี

### Workflow A: การจัดการ Template

```
สร้าง/แก้ไข Template (Draft)
  → ผู้ดูแลเอกสารตรวจสอบ
  → อนุมัติให้ใช้งาน
  → ตั้งเป็นเวอร์ชัน Active (เวอร์ชันเดิมกลายเป็น Archived)
  → ผู้ใช้ทั่วไปเลือกใช้ได้เฉพาะเวอร์ชัน Active
```

ข้อกำหนด

- Template แต่ละตัวมีเลขเวอร์ชัน (v1.0, v1.1) และวันที่เริ่มใช้
- เอกสารที่ออกไปแล้วต้องบันทึกว่าใช้ Template เวอร์ชันไหน เพื่อตรวจย้อนหลังได้
- Template ต้องมี placeholder มาตรฐาน เช่น `{{doc_no}}` `{{doc_date}}` `{{customer_name}}` `{{items_table}}` `{{total_amount}}` `{{approver_name}}`
- ห้ามลบ Template เก่า ให้เปลี่ยนสถานะเป็น Archived เท่านั้น
- ต้องมีตัวอย่าง (preview) ก่อนอนุมัติ

### Workflow B: การออกเอกสารและอนุมัติ

```
1. ผู้ขอเลือกประเภทเอกสาร + แบรนด์ + Template
2. ระบบให้เลขร่าง DRAFT-xxxx และเปิดฟอร์มกรอกข้อมูล
3. ผู้ขอกรอกข้อมูลและกดส่งขออนุมัติ
4. ระบบตรวจความครบถ้วน (validation) และหาเส้นทางอนุมัติตามกติกา
5. ผู้ตรวจตรวจสอบ → ผ่าน หรือ ตีกลับพร้อมเหตุผล
6. ผู้อนุมัติอนุมัติ → ระบบล็อกตัวนับ ออกเลขจริง บันทึกเวลาและผู้อนุมัติ
7. ระบบสร้าง PDF จาก Template + ข้อมูล แล้วบันทึกลงโฟลเดอร์ตามประเภทและเดือน
8. แจ้งเตือนผู้ขอ และส่งให้ลูกค้า (แนบไฟล์หรือลิงก์)
9. บันทึกลง audit log ทุกขั้นตอน
```

### กติกาเส้นทางอนุมัติ (ปรับตัวเลขตามจริง)

| เงื่อนไข | ผู้ตรวจ | ผู้อนุมัติ |
|---|---|---|
| เอกสารทั่วไป ไม่เกี่ยวกับเงิน | ไม่ต้อง | หัวหน้าฝ่าย |
| ยอดไม่เกิน 30,000 บาท | ผู้ประสานงาน | หัวหน้าฝ่าย |
| ยอด 30,001 - 200,000 บาท | ผู้ประสานงาน | ผู้จัดการ |
| ยอดเกิน 200,000 บาท | ผู้จัดการ | เจ้าของกิจการ |
| สัญญาและใบลดหนี้ทุกวงเงิน | ผู้จัดการ | เจ้าของกิจการ |
| ส่วนลดเกิน 20% ของราคาปกติ | ผู้จัดการ | เจ้าของกิจการ |

เพิ่มกติกาเสริม

- ถ้าผู้อนุมัติไม่ตอบภายใน 24 ชั่วโมง ให้เตือนซ้ำ และภายใน 48 ชั่วโมงให้ escalate ขึ้นระดับถัดไป
- ต้องมีระบบมอบอำนาจชั่วคราว (delegation) สำหรับช่วงลาหรือไปต่างประเทศ
- การอนุมัติต้องระบุความเห็นได้ และการตีกลับ **ต้องบังคับ** ให้ระบุเหตุผล

### Workflow C: การแก้ไขและยกเลิก

```
เอกสารสถานะ ISSUED ขึ้นไป
  → ขอแก้ไข: สร้าง revision ใหม่ (REV.02) ใช้เลขเดิม ฉบับเก่าเป็น SUPERSEDED
  → ขอยกเลิก: ต้องมีเหตุผล + ผู้อนุมัติระดับเดียวกับตอนออก → สถานะ VOID
  → เอกสารภาษีที่ยกเลิก ต้องออกใบลดหนี้แทน ห้าม VOID เฉย ๆ ถ้าส่งให้ลูกค้าแล้ว
```

| เอกสารถูกตีกลับ | ผู้ขอ | LINE + อีเมล |
| เอกสารอนุมัติแล้ว | ผู้ขอ | LINE |
| ค้างอนุมัติเกิน 24 ชม. | ผู้อนุมัติ | LINE (เตือนซ้ำ) |
| ค้างอนุมัติเกิน 48 ชม. | ระดับถัดไป | LINE + อีเมล |
| ใบเสนอราคาใกล้หมดอายุ | ผู้ขอ | LINE |
| ใบแจ้งหนี้ครบกำหนดชำระ | ฝ่ายบัญชี | อีเมล |
| ตรวจพบเลขข้าม | Admin | อีเมล (รายงานรายเดือน) |

ข้อความแจ้งเตือนต้องมีลิงก์เปิดเอกสารได้โดยตรง และแสดง 3 ข้อมูลอย่างน้อย คือ ประเภทเอกสาร ชื่อลูกค้า และยอดเงิน

## 10. ตัวเลือกเทคโนโลยี

### ตัวเลือกที่ 1: Google Workspace + Apps Script (แนะนำสำหรับเริ่มต้น)

- ข้อมูล: Google Sheets
- Template: Google Docs / Slides
- ตรรกะ: Apps Script
- ไฟล์: Google Drive
- ฟอร์ม: Apps Script Web App หรือ AppSheet

ข้อดี: ต้นทุนต่ำ เริ่มได้ทันที ทีมคุ้นเคยกับ Sheets อยู่แล้ว ทำ PDF จาก Docs ได้ในตัว
ข้อเสีย: ช้าลงเมื่อเอกสารเกินหลักหมื่นแถว การล็อกตัวนับต้องเขียนเองอย่างระมัดระวัง สิทธิ์ระดับแถวทำได้จำกัด

### ตัวเลือกที่ 2: No-code Database (Airtable / NocoDB / Baserow)

ข้อดี: สร้าง view และสิทธิ์ได้ง่ายกว่า มี automation ในตัว
ข้อเสีย: ค่าใช้จ่ายรายเดือนต่อผู้ใช้ การทำ PDF ต้องพึ่งเครื่องมือเสริม

### ตัวเลือกที่ 3: Web App เต็มรูปแบบ (Next.js + PostgreSQL/Supabase)

ข้อดี: ควบคุมได้ทุกอย่าง ตัวนับใช้ transaction ของฐานข้อมูลจริง รองรับการเติบโตระยะยาว
ข้อเสีย: ใช้เวลาพัฒนามากกว่า มีค่าดูแลระบบต่อเนื่อง

### คำแนะนำ

เริ่มด้วยตัวเลือกที่ 1 เพื่อพิสูจน์ว่ากติกาและ workflow ใช้ได้จริงกับหน้างาน แล้วค่อยย้ายไปตัวเลือกที่ 3 เมื่อปริมาณเอกสารเกิน 300 ฉบับต่อเดือน หรือเมื่อต้องการให้ลูกค้าเข้ามาดูเอกสารเองได้ ออกแบบโครงสร้างตารางตามข้อ 8 ตั้งแต่วันแรก จะย้ายระบบได้โดยไม่ต้องรื้อ

## 12. เกณฑ์ตรวจรับ (Acceptance Criteria)

ระบบจะถือว่าผ่านเมื่อทดสอบทุกข้อต่อไปนี้ได้ผลตามที่ระบุ

1. กดอนุมัติเอกสาร 2 ฉบับพร้อมกันจากคนละเครื่อง ต้องได้เลขต่างกันและเรียงต่อเนื่อง
2. เอกสารที่ยังไม่อนุมัติ ต้องไม่ปรากฏเลขจริงในทุกหน้าจอและทุกไฟล์
3. ลบเอกสารที่ออกเลขแล้วต้องทำไม่ได้ แม้ผ่านสิทธิ์ Admin (ทำได้เพียง VOID)
4. แก้ไขเอกสารสถานะ ISSUED ต้องถูกปฏิเสธที่ระดับฐานข้อมูล ไม่ใช่แค่ซ่อนปุ่ม
5. ตีกลับโดยไม่กรอกเหตุผลต้องทำไม่ได้
6. ผู้สร้างเอกสารต้องไม่ปรากฏเป็นตัวเลือกผู้อนุมัติของเอกสารฉบับนั้น
7. เอกสารยอดเกิน 200,000 บาท ต้องวิ่งไปหาผู้อนุมัติระดับสูงสุดเสมอ
8. PDF ที่สร้างต้องแสดงเลขที่เอกสาร ชื่อผู้อนุมัติ และวันที่อนุมัติถูกต้อง
9. รายงานตรวจความต่อเนื่องต้องจับเลขข้ามได้ในการทดสอบที่จงใจสร้างเลขข้าม
10. audit log ต้องบันทึกทุกการเปลี่ยนสถานะ พร้อมผู้ทำและเวลา

## 13. ความเสี่ยงและการรับมือ

| ความเสี่ยง | ผลกระทบ | การรับมือ |
|---|---|---|
| เลขซ้ำจากการกดพร้อมกัน | เอกสารภาษีผิด ตรวจสอบยาก | ล็อกตัวนับ + ทดสอบ concurrency ก่อนใช้จริง |
| ทีมกลับไปทำเอกสารนอกระบบ | ข้อมูลไม่ครบ ระบบไร้ประโยชน์ | ทำให้ออกเอกสารในระบบเร็วกว่าทำมือ + ปิดไฟล์ Template เก่าทั้งหมด |
| ผู้อนุมัติไม่กดอนุมัติ งานค้าง | ส่งเอกสารให้ลูกค้าช้า | เตือนซ้ำอัตโนมัติ + ระบบมอบอำนาจ + Dashboard เอกสารค้าง |
| ข้อมูลเสียหายหรือถูกลบ | สูญเสียหลักฐานทางบัญชี | สำรองข้อมูลอัตโนมัติรายวัน เก็บย้อนหลัง 12 เดือน |
| Template ผิดเวอร์ชัน | เอกสารส่งลูกค้าผิดรูปแบบ | บังคับใช้เฉพาะเวอร์ชัน Active และบันทึกเวอร์ชันในทุกเอกสาร |
| เปลี่ยนรหัสแบรนด์กลางทาง | เลขเก่าใหม่ปนกัน | ล็อกรหัสตั้งแต่ Phase 0 หากต้องเปลี่ยน ให้เริ่มชุดเลขใหม่ในปีถัดไป |

## 14. คำถามที่ต้องตัดสินใจก่อนเริ่มพัฒนา

1. แต่ละแบรนด์อยู่ใต้นิติบุคคลเดียวกันหรือแยกกัน เพราะกำหนดว่าจะแยกชุดเลขภาษีหรือไม่
2. ปัจจุบันออกเอกสารประมาณกี่ฉบับต่อเดือน และมีผู้ใช้งานกี่คน
3. เลขล่าสุดของแต่ละประเภทที่ออกไปแล้วคือเลขอะไร ต้องรันต่อหรือเริ่มชุดใหม่
4. ต้องการให้ลูกค้ากดยอมรับใบเสนอราคาออนไลน์ได้หรือไม่ (มีผลต่อการเลือกเทคโนโลยี)
5. ทีมบัญชีหรือสำนักงานบัญชีต้องการรับข้อมูลในรูปแบบใด
6. มีเอกสารย้อนหลังที่ต้องนำเข้าระบบหรือไม่ ถ้ามี ย้อนหลังกี่ปี
7. ใช้ปี ค.ศ. หรือ พ.ศ. ในเลขที่เอกสาร (แนะนำ ค.ศ. เพื่อการเรียงลำดับและการเชื่อมต่อระบบ)
